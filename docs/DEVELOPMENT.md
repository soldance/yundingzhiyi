# 开发方式、命令与规范

> **开工前必读。** 本文件定义了本项目的开发流程、编码规范、提交规范与验证清单。

---

## 1. 环境要求

| 项 | 版本 | 说明 |
|---|---|---|
| Node.js | **≥ 22** | 使用内置 `fetch`，不引入 HTTP 客户端库 |
| 包管理器 | **pnpm** | monorepo workspace 支持更好 |
| Git | ≥ 2.40 | — |
| 操作系统 | 不限 | 命令示例同时给出 PowerShell 与 POSIX 两种写法 |

### 1.1 国内网络加速

依赖安装使用国内镜像，避免拉取失败：

```bash
pnpm config set registry https://registry.npmmirror.com
```

## 2. 常用命令

> 以下命令在仓库根目录执行。命令名以实际的 `package.json` scripts 为准，实现时需保持与本表一致。

| 命令 | 作用 |
|---|---|
| `pnpm install` | 安装依赖 |
| `pnpm dev` | 同时启动后端与前端开发服务 |
| `pnpm dev:server` | 仅启动后端 |
| `pnpm dev:web` | 仅启动前端 |
| `pnpm build` | 构建全部产物 |
| `pnpm typecheck` | **类型检查（不产出文件）** |
| `pnpm test` | 运行单元测试 |
| `pnpm sync` | 同步游戏数据（抓取 + 清洗 + 校验） |
| `pnpm verify` | 数据完整性校验 |
| `pnpm lint` | 代码检查 |

### 2.1 命令的定位

- **`pnpm typecheck` 是本项目最重要的自动化闸门。** 契约层与实现不一致时，它会立刻报错。任何实现类任务在交付前都必须跑通它。
- **`pnpm sync` 需要网络**，首次运行会下载约 23MB 的数据文件。后续运行会先比对版本，版本未变则跳过。
- **`pnpm verify` 不需要网络**，仅校验已落盘的数据包。

## 3. 编码规范

### 3.1 语言

全部使用 **TypeScript**。

### 3.2 硬性约束

这些约束来自实测，违反会导致运行时错误：

```ts
// ❌ 禁止 enum：类型擦除模式下不可用
enum Tier { T0 = "T0" }

// ✅ 改用联合类型
type Tier = "T0" | "T1" | "T2" | "T3";
```

```ts
// ⚠️ 本地模块导入统一带 .ts 扩展名
// 这样将来若启用 Node 原生类型擦除运行能力，无需改动
import { COST_COLORS } from "./constants.ts";
```

其他禁止项：

- 禁止 `namespace`
- 禁止构造函数参数属性（`constructor(private x: number)`）
- 禁止旧式装饰器

### 3.3 契约

- **不得修改 `packages/shared/`**
- **不得在业务代码中重复定义契约中已有的类型**，哪怕只是"加个字段"
- 需要业务专用的扩展类型时，使用 `extends` 或 `Pick` / `Omit` 组合，不复制字段

### 3.4 模块

- **不在导入时产生副作用**：不在模块顶层发起网络请求或写文件
- **数据读取必须经过 `packages/server/src/store/`**，不得直接读文件
- 导出使用具名导出，不使用默认导出（便于重命名与静态分析）

### 3.5 错误处理

- **数据校验失败必须显式抛错**，不允许降级、不允许猜测、不允许静默跳过
- 面向用户的错误信息使用中文，面向日志的堆栈保持原始

```ts
// ❌ 静默降级：错误被吞掉，调用方以为成功了
const set = setData.find(x => x.name === "Set18") ?? setData[0];

// ✅ 显式失败
if (real.length < 50) {
  throw new Error(
    `赛季定位校验失败：期望 Set ${expected}，实际匹配到 ${real.length} 个英雄。` +
    `疑似 Community Dragon 数据结构变更，请先核对数据源。`
  );
}
```

### 3.6 规模

**单文件不超过 300 行。** 超出时应拆分。

这是硬约束而非偏好：文件过大时，接手者会把注意力消耗在理解现有代码上，产出质量明显下降。

## 4. Git 规范

### 4.1 提交信息格式

```
type(scope): 说明
```

- 第一行 **≤ 72 字符**
- `type` ∈ `feat` / `fix` / `docs` / `chore` / `test` / `refactor` / `perf` / `style`
- 使用中文描述

示例：

```
feat(store): 实现数据访问层与内存缓存
fix(engine): 修正羁绊计数未排除召唤物的问题
docs(architecture): 补充版本指纹的三重校验说明
```

### 4.2 🔴 提交前必做的两个机械动作

**动作 1：确认暂存区内容**

```bash
git diff --cached --name-only
```

输出**必须恰好**是本次打算提交的文件。若出现预期之外的文件（尤其是此前 `git rm --cached` 遗留的删除记录），停下来处理，改用 `git commit -- <已跟踪路径>`。

**动作 2：核对提交结果**

```bash
git show --stat HEAD
```

确认文件清单与预期一致。错了用 `git reset --soft HEAD~1` 撤回重做。

### 4.3 严格禁止

- ❌ **不要 `git add -A` / `git add .`** —— 逐个 `git add <具体文件>`，且先看 `git status`
- ❌ **不要提交未明确打算提交的文件**
- ❌ 不要在 commit message 中加入工具署名或协作署名
- ❌ 不要 `git push --force`，除非明确要求并确认后果

### 4.4 一个提交只做一件事

保持原子提交，便于将来单独 `git revert`。

### 4.5 常见陷阱

| 陷阱 | 说明 |
|---|---|
| `.gitignore` 对**已跟踪文件无效** | 要移除须 `git rm --cached <file>` |
| `git rm --cached` 的删除会**一直挂在暂存区** | 后续任何 `git commit` 都会带上，直到某次提交包含它 |
| `git commit -- <路径>` **不能提交未跟踪文件** | 会报 `pathspec did not match`；须先 `git add` |
| `git clean -fd` **永久删除且不进回收站** | 先用 `git clean -nd` 空跑确认 |

## 5. 任务卡格式

每项工作以任务卡形式下发。任务卡**必须**包含五要素。

```markdown
## 目标
<一句话，明确到可判定>

## 文件清单（只准动这些）
- packages/server/src/store/loadPack.ts
- packages/server/src/store/loadPack.test.ts

## 契约引用
- 必须实现 `ChampionsResponse`（见 docs/COMPONENT-API.md §4.2）
- 必须返回 `VersionFingerprint` 字段（见 §2.1）

## 验收标准（必须机械可判定）
- [ ] `pnpm typecheck` 退出码为 0
- [ ] `pnpm test` 全绿，且新增测试覆盖 X 场景
- [ ] 命令 `pnpm verify` 输出包含 "set 18 / patch 18.3"
- [ ] 文件 `data/packs/set18/champions.json` 存在且 champions 数组长度 ≥ 60

## 禁止事项
- 不得修改 `packages/shared/**`（契约层只读）
- 不得新增运行时依赖，除非在报告中说明理由
- 不得改动 `<他人负责的文件>`

## 阻塞处理
- 发现契约不合理 → **停止工作**，在报告中说明：现有定义的问题、建议变更、影响范围
- 不得自行修改契约或绕过
```

### 5.1 验收标准的写法

**可接受**：

- ✅ 文件存在于指定路径
- ✅ 内容包含指定段落 / 数组长度满足条件
- ✅ 命令退出码为 0
- ✅ 字段与 schema 一致

**不可接受**：

- ❌ "功能正常"
- ❌ "应该没问题"
- ❌ "看起来对"
- ❌ "已完成"

### 5.2 交付报告要求

1. **只报告实际观察到的结果**，禁止推测
2. 无法验证的部分**明确说明"未验证"及原因**
3. 附上实际执行的命令与真实输出片段
4. 说明产物的**绝对路径**

### 5.3 完成后必须清理

- 关闭启动的本地服务
- 删除临时数据库（`data/*.db`）
- 删除缓存与测试输出目录
- 确认 `git status` 中无意外残留

## 6. 验证清单

交付前逐项确认：

- [ ] `pnpm typecheck` 通过
- [ ] `pnpm test` 通过（新增逻辑有对应测试）
- [ ] 数据类改动：`pnpm verify` 通过
- [ ] 产物文件存在于报告所述的路径
- [ ] **只修改了任务卡文件清单中的文件**（用 `git status` 核对）
- [ ] 未修改 `packages/shared/**`
- [ ] 未新增未经说明的依赖
- [ ] 临时资源已清理
- [ ] 报告中无推测性表述

## 7. 数据相关工作的特别要求

涉及数据同步与清洗时，额外遵守：

### 7.1 三条必守规则

1. **用 `number` 字段定位赛季，绝不用 `name` 字段**（该字段实测会撒谎）
2. **`apiName` 前缀二次校验**，匹配数不足则显式抛错
3. **过滤非英雄条目**（道具与召唤物需分流到 `items` / `summons`）

详见 [AGENTS.md §2](../AGENTS.md#2-已知的数据陷阱务必先读)。

### 7.2 描述文本清理

数据源中的描述含占位符与标记，需清理：

| 原始 | 处理后 |
|---|---|
| `@HPBurnPerSecond*100@%` | `X%`（保留语义或标注占位） |
| `<br>` `<bright>` `</bright>` | 移除 |
| `\r\n` | 统一为空格或换行 |

**要求**：清理规则需有测试覆盖，且清理后不得丢失关键信息。无法可靠解析的占位符**保留原文并标注**，不得猜测数值。

### 7.3 校验器要求

`pnpm verify` 至少检查：

- 版本指纹字段完整
- 英雄数量在合理区间（当前赛季约 60~90）
- 每个英雄的费用在 1~5
- 每个英雄至少有一个羁绊（召唤物除外）
- 每件成装的 `composition` 长度为 2
- 每个纹章的 `emblemTrait` 都在羁绊列表中存在
- 所有阵容引用的英雄、装备、羁绊名称都能在数据包中找到

**最后一条最重要**：它防止阵容库出现"引用了不存在的英雄"这种静默错误。

## 8. 常见问题

### 8.1 数据同步失败

先确认能访问 `raw.communitydragon.org`。若为网络问题，检查代理设置；若为数据结构变更，按错误信息定位具体校验项。

### 8.2 赛季定位校验失败

说明 Community Dragon 的数据结构可能变化。**不要放宽校验阈值来"修好"它**——先人工核对数据源的实际结构，确认后再调整。

### 8.3 类型检查报契约不符

说明实现与契约层不一致。**先确认是哪一边错了**：

- 实现写错了 → 改实现
- 契约有问题 → **停止并上报**，不要自行修改契约

### 8.4 端口被占用

后端默认端口可通过环境变量覆盖。若需更换，避免硬编码端口。
