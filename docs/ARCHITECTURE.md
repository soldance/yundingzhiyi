### 进程结构

**单进程**：后端进程同时承担 API 服务、数据同步、LLM 代理。前端由 Vite 构建为静态文件后由后端托管，或开发期由 Vite dev server 独立提供。

不采用多服务拆分的原因：所有负载都是轻量的本地请求，拆分只会增加部署与调试复杂度。

## 3. 数据分层与存储

| 层 | 内容 | 存储形式 | 入库 | 变更频率 |
|---|---|---|---|---|
| **游戏数据** | 英雄 / 羁绊 / 装备 / 海克斯 / 数值 | JSON 数据包 | ✅ | 跟随游戏版本 |
| **知识层** | 策略 / 梯队基准 / 运营节奏 | Markdown | ✅ | 每赛季 / 每补丁 |
| **动态数据** | 会话 / 对话历史 | SQLite | ❌ | 每次使用 |

### 为什么这样分

- **游戏数据用 JSON**：可 diff、可版本化、随赛季整体替换、无依赖、可直接打开核对。数据量约数百 KB，数据库引擎的查询能力在此规模下没有用武之地。
- **知识层用 Markdown**：它正是要注入提示词的内容，且需要人审校。放在 git 里，内容变化进入版本历史。
- **动态数据用 SQLite**：会话是持续追加写的。若每个会话一个 JSON 文件，会话一多就是数百个小文件。

### 约束

> **所有数据读取必须经过数据访问层（`packages/server/src/store/`），业务代码不得直接读文件。**

这样将来若确需迁移到数据库，只需改动该层。

## 4. 数据包结构

一个赛季一份数据包，路径 `data/packs/set<N>/`：

```
data/packs/set18/
├─ version.json        版本指纹
├─ champions.json      英雄
├─ traits.json         羁绊
├─ items.json          装备
├─ augments.json       海克斯
├─ emblems.json        纹章（转职装备）
├─ summons.json        召唤物（不计羁绊，但阵容需要引用）
└─ economy.json        经济与刷新概率表  【待核准】
```

采用**分模块文件**而非单个大文件的原因：加载可按需、git diff 更可读、单个模块损坏不影响其他模块。

### 4.1 为什么需要 `summons.json`

云顶存在**被阵容引用但不计入羁绊**的单位（如召唤物、训练假人、特殊中立单位）。它们出现在阵容构成里，但计算羁绊激活时必须排除。

若把它们混在 `champions.json` 中，羁绊核验会算错——而且错得不明显。

### 4.2 装备分类

`items.json` 按分类组织，分类是**互斥且完备**的：

| 分类 | 说明 |
|---|---|
| `component` | 散件（基础装备） |
| `craftable` | 由散件合成的成装 |
| `artifact` | 神器 |
| `support` | 辅助装 |
| `radiant` | 光明装（成装的强化版本） |
| `emblem` | 纹章（转职装备，提供 +1 羁绊计数） |

**合成配方**：`craftable` 条目带 `composition: [散件A, 散件B]`。纹章的配方同样需要记录，因为它是羁绊计数的重要来源。

## 5. 数据流

### 5.1 同步流（离线，手动触发）

```
scripts/sync.ts
   │
   ├─ 1. 读取 Community Dragon 版本元数据（小文件，用于判断是否需要更新）
   │      └─ 版本未变 → 跳过，不拉取大数据文件
   │
   ├─ 2. 拉取 cdragon/tft/zh_cn.json（约 23MB）
   │
   ├─ 3. 【关键】赛季定位
   │      ├─ 取 setData[].number 最大者          ← 绝不用 name 字段
   │      ├─ 同 number 多份时取最后一个           ← 数组顺序即版本顺序
   │      ├─ apiName 前缀二次校验                 ← TFT18_ / DA_18_ / DA_Xxx18
   │      └─ 校验失败 → 显式抛错，不降级
   │
   ├─ 4. 清洗
   │      ├─ 过滤道具与召唤物（按费用与羁绊字段）
   │      ├─ 资源路径改写：.tex/.dds → .png，并小写化
   │      ├─ 羁绊档位解析：@{minUnits=2;maxUnits=3;style=1} → 结构化数组
   │      └─ 描述文本清理：移除 @变量@ 占位符与 <br> 等标记
   │
   ├─ 5. 分类装备、抽离纹章与召唤物
   │
   └─ 6. 写出数据包 + version.json（含 sourceUrls 与数据哈希）
```

### 5.2 请求流（在线）

```
浏览器 → GET /api/set/champions
   │
   ▼
路由处理器
   │
   ▼
数据访问层 ── 内存缓存（首次加载后常驻）
   │
   ├─ 版本指纹校验：数据赛季 vs 代码预期赛季
   │     ├─ 不一致 → 返回 409，附带提示信息
   │     └─ 补丁落后 → 正常返回，但响应头带警告标记
   │
   ▼
响应（含 meta 字段：set / patch / freshness）
```

**关键设计**：数据在首次请求时加载到内存并常驻。数据包仅数百 KB，无需引入缓存中间件。

### 5.3 追问流（涉及语言模型）

```
浏览器 → POST /api/session（若无会话）
       → GET  /api/chat/stream?session=...&action=recommend
   │
   ▼
后端
   ├─ 1. 组装提示词
   │      ├─ 常驻层：知识层内容（策略 + 梯队 + 赛季速查）
   │      │     ⚠️ 必须字节稳定，以命中模型侧的上下文缓存
   │      ├─ 白名单：当前赛季英雄 / 羁绊 / 装备名册
   │      └─ 按需层：局面中首次出现的实体详情（由 injected 集合控制）
   │
   ├─ 2. 流式调用模型，边转发 SSE 边累积完整回答
   │      └─ 模型可调用确定性工具：实体查询 / 羁绊核验
   │
   ├─ 3. 解析结构化输出块
   │
   ├─ 4. 【校验闸门】逐项比对数据文件
   │      ├─ 名称是否在白名单内
   │      ├─ 依据引用是否真实存在
   │      └─ 羁绊激活数是否与数据一致
   │
   └─ 5. 落库会话，推送 done 事件（含校验结果）
```

## 6. 版本指纹机制

### 6.1 指纹内容

`data/packs/set<N>/version.json`：

```jsonc
{
  "set": 18,
  "patch": "18.3",
  "syncedAt": "2026-09-29T06:31:08Z",
  "cdragonVersion": "...",     // Community Dragon 内容版本
  "gameVersion": "...",        // 游戏客户端版本
  "sourceUrls": ["..."],       // 数据来源链接，用于人工核对
  "hash": "..."                // 数据包内容哈希，用于一致性检查
}
```

### 6.2 三重校验

| 校验 | 触发条件 | 行为 |
|---|---|---|
| **赛季一致** | 数据包 `set` ≠ 代码预期赛季 | 🔴 **阻断**：接口返回 `409`，前端显示阻断页并提示重新同步 |
| **补丁新鲜** | 数据包 `patch` 落后于已知最新补丁 | 🟡 **警告**：正常返回，响应带 `freshness: "stale"`，前端显示警告条 |
| **数据源版本** | Community Dragon 版本号变化 | 🟢 **静默标记**：提示可更新，不影响使用 |

### 6.3 设计原则

> **过期数据仍然可用，但必须显式标注。**

- 直接拒绝服务，比给出过期结论更糟——用户失去了可用功能
- 静默给出过期结论最糟——用户会基于错误信息做决策

### 6.4 换季处理

赛季更换时：

1. 新建 `data/packs/set<N+1>/` 目录，**不覆盖**旧目录
2. 更新代码中的当前赛季常量（属于契约层变更，需走契约变更流程）
3. 旧赛季数据保留，可用于历史查询与对比

## 7. API 路由总览

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/meta` | 版本指纹、数据新鲜度、当前赛季信息 |
| `GET` | `/api/set/:module` | 赛季数据模块：`champions` / `traits` / `items` / `augments` / `emblems` |
| `GET` | `/api/comp` | 阵容梯队（推导结果） |
| `GET` | `/api/comp/:id` | 单套阵容详情，含依据的补丁改动 |
| `GET` | `/api/patch/current` | 当前补丁的结构化改动清单 |
| `POST` | `/api/session` | 新建会话 |
| `GET` | `/api/chat/stream` | 追问，返回 SSE |

**类型定义见 [COMPONENT-API.md](COMPONENT-API.md)。**

### 7.1 为什么对话用 GET + SSE

SSE 的标准客户端 `EventSource` 仅支持 GET。虽然也可以用 `fetch` + `ReadableStream` 处理 POST 流，但：

- 局面数据可能较大，放查询串有长度限制
- 因此设计为：**局面数据先通过 `POST /api/session` 提交并绑定到会话**，`GET /api/chat/stream` 只携带会话 ID 与指令

这样既保持标准 SSE 的简单性，又不受 URL 长度限制。

## 8. 推导引擎

### 8.1 职责边界

推导引擎是**纯计算模块**，不涉及 IO，不调用模型。输入为数据包与补丁改动清单，输出为阵容梯队。

```
输入：
  comps 基线（人工维护的阵容骨架）
  patch 改动清单（结构化）
  set 数据包（英雄 / 羁绊 / 装备数值）
        │
        ▼
  ① 改动映射：PatchChange → 受影响 Entity
  ② 角色判定：该 Entity 在每套阵容中是核心 / 挂件 / 无关
  ③ 增量计算：按规则得出每套阵容的强度增量 Δ
  ④ 梯队排序：基准强度 + Δ → 排序 → 划分梯队
        │
        ▼
输出：Comp[]，每套带 tier、score、reasons[]（依据的改动 ID）
```

### 8.2 关键要求

- **每套阵容的 `reasons` 必须非空**（除非该补丁确实未影响它）。这是"可溯源"的实现基础。
- **增量计算规则必须可单独测试**，规则参数集中在契约层常量中，便于调整。
- **不硬编码梯队**。梯队是算出来的。

### 8.3 待决策

**改动到强度的映射规则**是产品的核心算法，也是主观性最强的部分，尚未确定。规则确定前，推导引擎可以先用一个可替换的规则实现，并通过测试固定行为。

## 9. 输出校验闸门

模型输出的 JSON 必须经过校验才能返回前端。

| 校验项 | 判定 | 不通过的处理 |
|---|---|---|
| 英雄名在白名单内 | 精确匹配数据包中的 `name` | 标记该条为 `invalid` |
| 羁绊名存在 | 同上 | 标记 |
| 装备名存在 | 同上 | 标记 |
| 羁绊激活数与数据一致 | 用确定性函数重算 | **以重算结果为准**并标记修正 |
| `evidence` 引用真实存在 | 指向的 PatchChange ID 存在 | 无依据的结论降级标注 |

**校验结果必须返回前端并可视化**（例如编造的名称标红），而不是静默丢弃。用户看到"模型编造了一个不存在的英雄"这件事本身，比看到一句被悄悄修正的答案更有价值。

## 10. 数据库设计

仅用于动态数据。

```sql
-- 会话
CREATE TABLE session (
  id            TEXT PRIMARY KEY,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  set_number    INTEGER NOT NULL,   -- 会话创建时的赛季，用于历史回溯
  patch         TEXT    NOT NULL,
  state_json    TEXT                -- 当前局面（GameState 序列化）
);

-- 对话消息
CREATE TABLE message (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id    TEXT    NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  role          TEXT    NOT NULL,   -- user | assistant | tool
  content       TEXT    NOT NULL,
  structured    TEXT,               -- 模型输出的结构化块（校验后）
  created_at    INTEGER NOT NULL
);

CREATE INDEX idx_message_session ON message(session_id, created_at);
```

**设计要点**：

- `set_number` 与 `patch` 记录在会话上。历史会话在换季后仍可查看，但界面需标注"该会话基于旧版本"
- 不存储模型原始输出，只存校验后的结果与校验发现的问题
- 数据库文件位于 `data/`，已在 `.gitignore` 中排除

## 11. 错误处理约定

| 场景 | 行为 |
|---|---|
| 赛季不一致 | `409`，响应体含期望赛季与实际赛季，前端显示阻断页 |
| 数据包缺失 | `503`，提示先执行同步 |
| 数据包结构校验失败 | 启动时即失败（fail fast），不进入服务状态 |
| 会话不存在 | 静默新建会话，首个事件回传新 ID |
| 无可用模型密钥 | SSE 返回 `error` 事件，前端提示；**数据类功能不受影响** |
| 模型输出无结构化块 | `done` 事件的 `structured: null`，前端仅渲染文本 |
| 模型输出校验不通过 | 正常返回，但在结构化结果中标记 `invalid` 项 |

**统一原则**：数据类功能（阵容总览、数据速查）**不依赖语言模型**，模型不可用时必须保持完全可用。
