# 设计方案

> 本文档记录项目的核心设计决策及其理由。部分设计仍在讨论中，未冻结处已标注。

## 1. 设计出发点

### 1.1 这不是一个语言模型产品，是一个数据产品

本领域所有事实——谁是 5 费卡、哪个羁绊在几人口激活、某件装备提供多少属性、这个补丁削了哪个英雄多少攻击力——都是**外部给定的、变动的、有唯一正确答案的**。

语言模型的角色因此被压缩为两件事：

1. **理解**：把玩家的口语化问题翻译成对结构化数据的查询
2. **判断**：在事实确定的前提下做取舍与建议

这两件事都不该由模型"记住"。模型一旦试图记忆云顶知识，就必然在换季时输出上个赛季的阵容，**并且以完全自信的语气**。

因此贯穿全部设计的核心原则是：

> **事实来自数据，判断来自模型，两者的边界要划得非常清楚。**

### 1.2 差异化定位

参考市面已有工具后，本项目的价值不落在"展示当前强势阵容"上，而落在两处它们没有覆盖的地方：

| 缺口 | 本项目的回应 |
|---|---|
| 只给结论不给依据，玩家无法判断某个改动对自己手上阵容的影响 | **补丁驱动的可溯源推导**：每个梯队结论都能展开看到依据的改动条目与官方来源 |
| 赛季每约 4 个月清空重建，静态数据工具会静默输出过时结论 | **版本指纹校验**，赛季不一致时阻断而非降级 |

## 2. 领域建模：知识图谱

### 2.1 为什么不能只用文档检索

玩家的每个问题都需要**跨多个信息源做关联推理**：

| 问题 | 需要的信息与关联 |
|---|---|
| 这版本什么阵容强 | 补丁改动 → 英雄 → 羁绊 → 阵容组合 |
| 这件装备给谁 | 装备 → 英雄适配 → 该英雄所属阵容 |
| 我该 D 牌还是拉人口 | 阵容成型曲线 → 各费用刷新概率 → 当前等级 |
| 这三个海克斯选哪个 | 海克斯 → 阵容适配 → 当前场上英雄 |

朴素的文档切片加向量检索在这里会失效：它能召回"语义相似"的文本，但无法回答"**受影响的核心英雄分布在哪些阵容里**"这类结构性查询——而这恰恰是本项目的核心查询。

### 2.2 实体与关系

```
                      ┌─────────────┐
                      │   Patch     │  版本改动
                      │             │  「凯特琳 攻击力 80→70」
                      └──────┬──────┘
                             │ 改动影响
                             ▼
┌──────────┐  拥有   ┌─────────────┐  适配   ┌─────────────┐
│  Trait   │◄───────│  Champion   │───────►│    Item     │
│  羁绊     │        │   英雄       │        │   装备       │
└────┬─────┘        └──────┬──────┘        └─────────────┘
     │                     │
     │ 组成                │ 核心成员 / 可选替换
     ▼                     ▼
┌─────────────────────────────────────┐        ┌─────────────┐
│              Comp                   │◄───────│   Augment   │
│  阵容 = 英雄集合 + 羁绊激活 + 装备分配  │  适配   │   海克斯     │
└─────────────────────────────────────┘        └─────────────┘
                     ▲
                     │ 作用于
              ┌──────┴──────┐
              │  GameState  │  等级/金币/血量/场上英雄/装备/海克斯
              └─────────────┘
```

### 2.3 三层属性

每个实体都带三层属性，**分开存储、分开校验**：

| 层 | 内容 | 来源 | 权威性 |
|---|---|---|---|
| **事实层** | 费用、属性、羁绊阈值、装备配方、改动数值 | Community Dragon + 官方补丁公告 | 权威，**不可由模型生成** |
| **分析层** | 阵容强度、核心度、装备优先级、成型难度 | 从事实层**推导** | 可推导，需说明依据 |
| **判断层** | 该不该 D、该不该转、这个海克斯值不值 | 模型推理 | 主观，必须给理由 |

**划分这条界的意义**：事实层错了是 bug，可以自动检测；判断层错了是建议不佳，可以调优。两者混在一起就无法定位问题。

## 3. 核心机制：阵容是推导出来的，不是录入的

这是本设计中最关键的选择。

**常见做法**：人工或爬虫维护一张阵容表存入数据库，按补丁人工更新。缺点是每个补丁都要重新维护，且"为什么强"这个信息在录入时就丢失了。

**本项目的做法**：分成两条独立的线。

```
基准线 ── 人工维护，每赛季一次
  Comp 骨架：名称、核心英雄、装备分配、站位、成型曲线
        ↓
增量线 ── 每个补丁重算
  Patch 改动清单
    ↓ 映射到受影响英雄
  受影响英雄
    ↓ 映射到所属阵容 + 在阵容中的角色（核心 / 挂件）
  阵容强度增量 Δ
    ↓ 叠加到基准
  当前版本阵容梯队
```

### 收益

- **可审计**："这套阵容为什么是 T0？" → 因为本次补丁加强了它的核心卡 X，削弱了天敌 Y。每条都能点开看原始改动。
- **换补丁成本低**：只处理"这个补丁改了什么"，不必重新评估全部阵容。
- **自然产出运营建议**：改动作用于核心卡还是挂件，直接影响该阵容的强势期与 D 牌节奏。
- **规避静默失败**：基准线不变但增量每补丁重算，不会出现"界面显示 18.5 但阵容仍是 18.1 评估的"。

### 待定

补丁改动到强度增量的**映射规则**（例如"核心卡加强 5% 是否足以推上 T0"）是产品的核心算法，也是主观性最强的部分，尚待确定。

## 4. 推理机制

### 4.1 流水线

```
玩家输入（自然语言 / 结构化表单）
   │
   ▼
① 意图路由 ── 阵容查询 / 单点事实 / 局面决策
   │
   ▼
② 查询构造 ── 模型把口语翻译为结构化查询
   │
   ▼
③ 事实检索 ── 【纯代码】按图谱查询，只返回数据文件中真实存在的条目
   │
   ▼
④ 分析计算 ── 【纯代码】费用曲线、羁绊覆盖、刷新概率、
   │            阵容强度增量（补丁 delta 叠加）
   │
   ▼
⑤ 建议生成 ── 模型基于 ③④ 的结果组织语言、做取舍判断
   │
   ▼
⑥ 校验闸门 ── 【纯代码】拦截幻觉
```

### 4.2 分工边界

| 任务 | 归属 | 原因 |
|---|---|---|
| 英雄 / 羁绊 / 装备查询 | 代码 | 有唯一正确答案 |
| 升级经验、刷新概率、利息 | 代码 | 纯数学 |
| 羁绊激活判定 | 代码 | 有明确阈值 |
| 补丁改动 → 阵容强度增量 | 代码 | 可用规则计算 |
| 阵容排序 | 代码 | 由增量叠加得出 |
| 自然语言理解 | 模型 | 本质是翻译 |
| 局势取舍建议 | 模型 | 需要权衡，无唯一解 |
| 建议的表述与解释 | 模型 | 语言组织 |
| 异常局面处理 | 模型 | 需要灵活判断 |

### 4.3 幻觉三道闸门

云顶有数十个英雄与羁绊，模型凭空编造一个名字，玩家不容易一眼看穿。因此：

**闸门一 · 输入侧约束**
将当前赛季的英雄名、羁绊名、装备名作为**白名单**注入提示词，明确要求只能从名单中选择。模型被限制在封闭集合内，编造成本大幅上升。

**闸门二 · 输出侧校验**

要求模型输出结构化 JSON 而非纯文本：

```jsonc
{
  "answer": "建议优先做无尽之刃给凯特琳",
  "champions": ["凯特琳"],
  "traits": ["执法官"],
  "items": ["无尽之刃"],
  "evidence": [{ "source": "patch:18.3", "detail": "凯特琳攻击力 80→70" }]
}
```

后端逐项比对数据文件：

| 校验项 | 不通过的处理 |
|---|---|
| 英雄名是否在名册中 | 标记并拒绝显示该条 |
| 羁绊名是否存在 | 标记 |
| 装备名是否存在 | 标记 |
| `evidence` 引用是否真实存在 | 无依据的结论降级标注 |
| 羁绊激活人口是否与数据一致 | 数学校验，错误则修正 |

把校验结果渲染在界面上（例如编造的名称标红），比事后道歉更有用。

**闸门三 · 工具约束**
提供确定性的羁绊核验工具，并在提示词中规定：**给出终局阵容之前必须先调用核验**。同时在服务端对模型给出的目标阵容重新计算一次作为兜底。

## 5. 数据层设计

数据层是本项目风险最高的部分，设计上要求**出错必须响**。

### 5.1 数据来源与职责

| 数据 | 来源 | 更新频率 | 可靠性 |
|---|---|---|---|
| 英雄 / 羁绊 / 装备 / 数值 | Community Dragon `cdragon/tft/zh_cn.json` | 跟随游戏客户端版本 | 官方，**含原生中文** |
| 英雄头像等资源 | Community Dragon 资源目录 | 跟随版本 | 已验证可直连 |
| 补丁改动 | Riot 官方公告 | 每约 2 周 | 需解析 |
| 阵容基准线 | 人工维护 | 每赛季（约 4 个月） | — |

### 5.2 版本指纹

每份数据挂一个指纹：

```jsonc
{ "set": 18, "patch": "18.3", "cdragonVersion": "...", "syncedAt": "...", "sourceUrls": [] }
```

运行时三重校验：

| 校验 | 触发条件 | 行为 |
|---|---|---|
| 赛季一致 | 数据的 `set` 与代码预期不符 | **阻断**，提示需重新同步 |
| 补丁新鲜 | 数据 `patch` 落后于官方最新 | 界面警告条：结论可能过时 |
| 数据源版本 | Community Dragon 版本号变化 | 静默标记，提示可更新 |

> **过期数据仍然可用，但必须显式标注。** 直接拒绝服务比给出过期结论更糟；静默给出过期结论最糟。

### 5.3 已实测的数据陷阱

以下三条均已实际验证，且都属于**静默失败**——不报错，但结果是错的：

1. **`setData[].name` 字段不可信**
   当前赛季（Set 18）的数据块该字段实际写着 `"Set10"`。
   → 必须用 `number` 字段定位，再用英雄 `apiName` 前缀（`TFT18_` / `DA_18_` / `DA_Xxx18`）二次校验。
   → *若按 `name` 字段筛选，会拿到早已下线的赛季数据且完全不报错。*

2. **接口返回的是历史上所有赛季快照的合集**
   实测返回 35 个快照（Set 1 / 3 / 7 / 13 / 14 / 15 / 16 / 17 / 18），其中 Set 7 与 Set 13 各有多份版本快照。
   → 必须自行切出最新快照。

3. **非英雄条目混在英雄列表里**
   某赛季 91 条中有 23 条是道具与召唤物（纹章之书、训练假人、锻造器等）。
   → 通过费用取值与羁绊字段是否为空过滤。

### 5.4 存储划分

| 数据 | 存储 | 理由 |
|---|---|---|
| 游戏数据 | **JSON 数据包**，按赛季分目录 | 可 diff、可版本化、随版本整体替换 |
| 知识层（策略 / 梯队 / 运营节奏） | **Markdown + git** | 人可读可审校；正是要注入提示词的内容 |
| 动态数据（会话 / 对话历史） | **SQLite** | 持续追加写，单文件管理优于大量小文件 |

## 6. 界面设计

### 6.1 三个视图

**视图 A · 阵容总览（主视图）**
阵容卡片列表：费用描边头像、羁绊徽章、核心装备、运营节奏。每张卡片带可展开的「为什么是 T0」面板，列出依据的补丁改动条目与官方来源外链。

**视图 B · 局面咨询（决策入口）**
上半部分是结构化输入（等级、金币、血量、已有英雄、装备、海克斯），下半部分是自由提问。

保留结构化表单的原因：自然语言能表达"我 4-1 有 50 块血量 40"，但**容易漏项或误解**。表单保证关键信息不丢，自然语言作为补充。

输出形式为**结论 + 理由 + 依据**三段，而非一句话。

**视图 C · 数据速查**
英雄 / 羁绊 / 装备的可搜索列表。这一层看似附属，实际是**校验能力的可视化**——用户能自行查到真实数据，就不容易被模型带偏。

### 6.2 设计约束

- **「为什么强」默认折叠**：不干扰日常使用，但需要时随时可查。这是本项目区别于阵容榜的核心。
- **每条理由挂来源外链**：可一键核对官方公告。
- **补丁改动以色彩标识**：加强 / 削弱区分显示。
- **降级可用**：语言模型不可用时，视图 A 与 C 完全正常（它们是纯数据），仅视图 B 提示不可用。

### 6.3 视觉方向

定调为**暗色竞技科技感**，贴近游戏本体视觉语言：

- 主色采用游戏原生金色系而非通用蓝紫渐变，使 5 费卡的金边与主题色系自洽
- 费用色直接映射游戏（1 灰 / 2 绿 / 3 蓝 / 4 紫 / 5 金）
- 背景使用径向渐变加噪点纹理制造氛围，避免纯色平板
- 棋盘采用奇数行错位以模拟六边形网格

## 7. 明确不做

- ❌ 真实胜率 / 登场率统计的自动抓取（第三方站点无公开 API，页面结构变动即失效）
- ❌ 对局内存读取或模拟器插件（有账号风险）
- ❌ 截图视觉识别（需训练数据与独立模型服务，非核心价值）
- ❌ 用户系统与账号
