# 技术选型

> 本文档记录技术栈的选择及理由。所有环境相关结论均为**实测结果**，非推测。

## 1. 选型准则

常规项目看性能、生态、团队熟悉度。本项目的特殊之处在于：**代码由多个 AI 编码角色分工完成**，因此选型实际只看一件事：

> 这项技术让"多个执行者各写各的"更容易，还是更难？

由此得出三条准则：

| 准则 | 含义 |
|---|---|
| **零/低成本构建** | 任何"改完要等编译才能验证"的环节都会削弱执行者的自测闭环 |
| **契约显式** | 接口必须能被机器检查，不能靠自然语言描述 |
| **可独立验证** | 每项工作完成后必须能独立验证，不依赖其他部分是否就绪 |

## 2. 实测环境基线

| 能力 | 实测结果 | 对选型的影响 |
|---|---|---|
| 操作系统 | Windows 10 (10.0.19045) | 命令使用 PowerShell 语法 |
| Node.js | v22.22.0 | LTS 线，原生 `fetch`、`AbortSignal.timeout` |
| 包管理器 | npm 10.9.4 / pnpm 11.8.0 | 采用 pnpm（workspace 支持更好） |
| TypeScript | 未全局安装 | 作为项目 devDependency 引入 |
| 构建工具 | Vite / tsup / esbuild 均未全局安装 | 作为项目 devDependency 引入 |
| `node:sqlite` | 可用，WAL 模式可用，**但带实验性警告** | 见第 6 节 |
| 全局 `fetch` | 内置 | 无需引入 HTTP 客户端库 |

### 2.1 一个实测发现（记录备查）

Node 22.22 **可直接运行 `.ts` 文件**，无需任何编译步骤（类型擦除）。这对多执行者协作有潜在价值，但实测发现两个限制：

```ts
// 限制一：import 必须带 .ts 后缀，否则 ERR_MODULE_NOT_FOUND
import { COST_COLORS } from "./types.ts";   // ✅
import { COST_COLORS } from "./types";      // ❌

// 限制二：enum 直接抛 ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX
enum Tier { T0 = "T0" }                     // ❌ 必须改用联合类型
```

**结论**：该能力作为备选保留（未来若想彻底去掉后端构建步骤可用），但当前选型仍采用标准的 `tsup` 构建，因为：

- 前端无论如何需要 Vite 构建，统一流程比"前端构建、后端不构建"更易维护
- 避免 `.ts` 后缀与禁用 `enum` 这类非标准约束给执行者带来额外认知负担
- 标准工具链的报错信息更友好，更利于定位问题

## 3. 前端

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | **Vue 3.5** | 生态成熟；与团队既有经验一致（此前项目为 Vue）|
| 构建 | **Vite 7** | 构建速度快，开发体验好；产物为纯静态文件 |
| 语言 | **TypeScript** | 契约可被机器检查，是防接口漂移的主要手段 |
| 样式 | **Tailwind CSS v4** | 无需维护独立的样式文件；v4 配置更简洁 |
| 组件库 | **不引入**（自研） | 见下 |
| 图标 | `lucide-vue-next` | 轻量，不绑架视觉风格 |
| 状态 | Vue 响应式（**不引入 Pinia**） | 应用状态简单，引入状态库属于过度设计 |
| 动效 | CSS 优先，必要时 `motion-v` | 减少依赖 |

### 3.1 为什么不引入组件库

本项目的界面构成是**棋子头像卡、羁绊徽章、装备图标、4×7 棋盘网格**——这些全是自定义 DOM 结构，组件库提供的表格、表单、弹窗等通用组件在这里用不上。

更关键的是：组件库的默认视觉语言会限制美化上限，而**界面质量是本项目相对同类工具的差异化优势之一**。引入组件库等于主动放弃这部分优势，却换不来实际收益。

### 3.2 样式方案

采用 **Tailwind v4 + CSS 变量 design token**：

```css
:root {
  /* 主色采用游戏原生视觉语言，而非通用蓝紫渐变 */
  --bg-base:    #0B0E14;   /* 深墨蓝底 */
  --bg-panel:   #121826;   /* 面板 */
  --accent-gold: #C8AA6E;  /* 高亮、梯队标记、核心卡 */
  --accent-cyan: #4FD1C5;  /* 数据、链接、状态 */
  --text-primary: #E8E6E3; /* 暖白，非纯白 */

  /* 费用色直接映射游戏 */
  --cost-1: #9AA4B2;
  --cost-2: #3E9B4F;
  --cost-3: #2E7CD6;
  --cost-4: #A24BD6;
  --cost-5: #E0B24C;
}
```

设计要点：

- **主色用金而非蓝紫**：金色在暗底上的对比度与"稀有度"暗示正好契合云顶的费用体系，5 费卡金边与主题色系自洽
- **暖白代替纯白**：降低长时间阅读的刺眼感
- **背景需有氛围**：径向渐变网格 + 噪点纹理叠加，避免纯色平板的廉价感
- **字体需有辨识度**：中文正文与标题选择可读性好的非系统字体，数字与拉丁字符采用窄体科技感字体

## 4. 后端

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node.js 22** | 与前端同语言，契约类型可前后端共享 |
| 框架 | **Hono** | 极轻量、TypeScript 原生友好、原生支持 SSE |
| 服务适配 | `@hono/node-server` | 在 Node 上运行 Hono |
| 校验 | **Zod** | 同时用于 API 入参校验与**模型结构化输出的校验** |
| 构建 | `tsup`（基于 esbuild） | 构建耗时在秒级 |
| 日志 | 结构化 JSON 输出 | 便于排查与后续分析 |

### 4.1 为什么不是 Express / Fastify

路由数量有限（约 10 个）。Express 带来的价值远小于它增加的"执行者需要理解框架约定"的成本。Hono 的 API 更贴近标准 `Request` / `Response`，中间件模型也更简单。

### 4.2 为什么不是 Python

参考项目中有使用 Python 的案例，方案本身没问题。但本项目选择 Node 的决定性理由不是运行时性能，而是：

> **前后端统一 TypeScript，可以让契约类型定义只写一份，前后端共同 import。**

这直接消除了"前端以为字段叫 A、后端写的是 B"这类问题的可能性——类型检查会在改完代码时立刻发现，而不是等到集成时。对多执行者分工的场景，这是决定性优势。

## 5. 契约层

```
packages/shared/          ← 唯一的契约真源
  └─ src/
      ├─ entities.ts      Champion / Trait / Item / Augment / Comp / PatchChange
      ├─ api.ts           每个路由的请求与响应类型
      └─ constants.ts     费用、梯队、羁绊阈值等枚举（用联合类型，不用 enum）
```

**规则**：

- 契约层是**只读**的。执行者发现契约不合理时须停下来上报，不得自行修改——否则所有基于旧契约的工作成果全部作废。
- 数据文件的字段规范同样在此定义，并由 Zod schema 校验。

## 6. 数据层

采用**三分法**，而非单一存储：

| 数据 | 存储 | 理由 |
|---|---|---|
| **游戏数据**：英雄 / 羁绊 / 装备 / 海克斯 / 数值 | **JSON 数据包**，按赛季分目录 | 可 diff、可版本化、随版本整体替换、无依赖、可直接打开核对 |
| **知识层**：策略 / 梯队 / 运营节奏 | **Markdown + git** | 人可读可审校；正是要注入提示词的内容；数据变化进入版本历史 |
| **动态数据**：会话 / 对话历史 | **SQLite** | 持续追加写入 |

### 6.1 为什么动态数据用 SQLite

会话数据是**持续追加写**的。若用「每个会话一个 JSON 文件」，会话一多就是数百个小文件，读取与管理都会变得困难。

**驱动选择**：`better-sqlite3` 优于内置 `node:sqlite`：

| 维度 | `node:sqlite` | `better-sqlite3` |
|---|---|---|
| 依赖 | 内置 | 需要安装（含原生模块） |
| 稳定性 | **实验性**，API 可能变化，每次启动打警告 | 成熟稳定 |
| API 风格 | 同步 | **同步**，写法简单 |
| 生态熟悉度 | 较新 | 广泛使用 |

### 6.2 为什么游戏数据不用数据库

当前赛季约 70 个英雄、26 个羁绊、数百件装备，全量加载到内存不过数百 KB。使用数据库引擎带来的查询能力在此数据量下没有用武之地，却会牺牲数据可读性与可 diff 性。

**约束**：所有数据读取必须经过统一的数据访问层，不直接读文件。将来若确需迁移到数据库，只需改动该层。

## 7. 仓库结构

采用 monorepo，目录划分同时承担**文件所有权边界**的职责——每个执行者只操作一个目录，从物理上避免并发写同一文件。

```
yundingzhiyi/
├─ packages/
│  ├─ shared/          契约层：类型定义（前后端共享，只读）
│  ├─ server/          后端：Node + Hono
│  ├─ web/             前端：Vue 3 + Vite
│  └─ data/            数据同步与知识层加载
├─ data/
│  ├─ packs/           各赛季数据包（JSON，随仓库分发）
│  └─ knowledge/       知识层（Markdown，随仓库分发）
└─ docs/               设计文档
```

## 8. 编码规范

### 8.1 通用

- 全部使用 TypeScript
- 导入本地模块时**带 `.ts` 扩展名**（若将来启用 Node 原生运行能力，这是前提）
- **不使用 `enum`**，改用联合类型与 `as const` 对象
- 不使用 `namespace`、构造函数参数属性、旧式装饰器
- 模块内不产生副作用（不在导入时执行网络请求或文件写入）

### 8.2 依赖管理

保持依赖精简。引入新依赖前需说明：它解决了什么问题、是否能用标准库替代、维护活跃度如何。

## 9. 备选方案记录

| 决策点 | 采用 | 考虑过但未采用 | 原因 |
|---|---|---|---|
| 后端语言 | Node + TypeScript | Python + FastAPI | 前后端契约无法共享类型 |
| 后端框架 | Hono | Express / Fastify | 路由少，框架收益低 |
| 前端框架 | Vue 3 | React | 与既有经验一致 |
| 组件库 | 自研 | Element Plus / Naive UI | 限制美化上限，通用组件用不上 |
| 状态管理 | Vue 响应式 | Pinia | 状态简单，属过度设计 |
| 动态数据 | SQLite | JSON 单文件 | 追加写场景下文件数失控 |
| 游戏数据 | JSON 数据包 | SQLite | 数据量小，可读性与 diff 性更重要 |
| 后端构建 | tsup | Node 原生类型擦除 | 统一流程，避免非标准约束 |
