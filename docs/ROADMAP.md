# 路线图

> 当前状态：**设计阶段**，以下为规划，尚未开始编码。

## 1. 推进原则

本项目采用「先验证地基、再横向铺开」的顺序，原因是**风险最高的环节不是语言模型，而是数据层**：

- 云顶每约 4 个月更换赛季，会清空全部英雄、羁绊、装备
- 若数据层没有赛季校验机制，产品会在换季时静默输出过时阵容，且无人察觉
- 数据源的字段缺陷（见 [DESIGN.md 第 5.3 节](DESIGN.md#53-已实测的数据陷阱)）全部属于静默失败类型

因此**数据层必须先做透并建立自动校验**，界面与模型接入后置。

另一条原则：**阶段 1~3 完全不依赖语言模型**。先用真实数据把界面跑起来，确认数据正确、图谱关系合理。这样出问题时能立刻区分是"数据错了"还是"模型胡说"。

## 2. 阶段划分

| 阶段 | 内容 | 依赖语言模型 |
|---|---|---|
| **阶段 1** | 数据通道：同步、赛季校验、清洗、落盘 | 否 |
| **阶段 2** | 知识层：实体与关联、阵容基准线、种子数据 | 否 |
| **阶段 3** | 后端：数据访问层、数据类 API、版本指纹校验 | 否 |
| **阶段 4** | 前端：阵容总览、数据速查、版本状态条 | 否 |
| **阶段 5** | 补丁层：官方公告抓取与结构化 | 是 |
| **阶段 6** | 推导层：补丁增量到阵容强度的计算 | 是 |
| **阶段 7** | 问答层：推理流水线、局面输入、输出校验闸门 | 是 |
| **阶段 8** | 决策增强：同行检测、转型建议、阵容码 | 是 |

**阶段 1~4 可独立交付一个有价值的版本**（可浏览的阵容库 + 数据速查 + 版本状态）。这既是验证地基的手段，也是可发布的第一个里程碑。

## 4. 工作拆解

### 4.1 拆解原则

拆解方式基于一个约束：**代码由多个执行者分工完成，而执行者之间没有文件锁**。两个执行者同时修改同一文件时，后写的结果会覆盖先写的，且**不会报错**。

因此采用**按层横向切分**，而非按功能纵向切分：

```
❌ 纵向切分（按功能）              ✅ 横向切分（按层）
┌─────────────┐                 ┌───────────────────────────┐
│ 阵容功能     │                 │ 契约层  ← 所有工作依赖此层   │
│  ├ 前端      │                 ├───────────────────────────┤
│  ├ 后端      │                 │ 数据层 │ 后端层 │ 前端层   │  ← 可并行
│  └ 数据      │                 └───────────────────────────┘
└─────────────┘
```

纵向切分的问题：

1. **必然冲突**：多个功能都要改同一批入口文件
2. **无法独立验证**：每个功能都跨越完整技术栈，验收需要整个系统就绪
3. **上下文膨胀**：每个执行者都要理解整个项目

横向切分后每个执行者只操作一个目录，物理上不可能冲突。

### 4.2 关键路径：契约先行

**第一项工作不能是任何功能，必须是契约冻结。**

```
契约层（必须最先完成，是全部并行工作的前提）
  ├─ packages/shared/src/entities.ts   实体类型
  ├─ packages/shared/src/api.ts        每个路由的请求与响应类型
  └─ packages/shared/src/constants.ts  费用、梯队、阈值等常量
```

契约冻结之后，前端、后端、数据层可以同时开工。且任何一方与契约不符时，类型检查会立刻报错——这把"接口不一致"从集成时才发现提前到改完就发现。

**契约是只读的。** 执行过程中发现契约不合理，须停下上报，不得自行修改。

### 4.4 依赖关系

```
0-1 契约 ──┬─→ 0-2 骨架 ──→ 1-B1 ──→ 1-B2 ──→ 1-B3
           │
           ├─→ 数据线 (1-D1 → 1-D2 → 1-D3)
           │
           ├─→ 3-P1 / 3-P2 ──→ 3-P3 强度推导 ──→ 3-P4 校验闸门
           │
           └─→ 前端线 (2-F1 → 2-F2 → 2-F3 ~ 2-F6)   ← 完全独立
```

**关键路径**：`0-1 → 0-2 → 1-B1 → 1-B2 → 3-P3 → 3-P4 → 4-1`

### 4.5 工作项规模约束

单项工作控制在 **2~5 个文件、单文件不超过 300 行**。

这是硬约束而非偏好：文件过大时，执行者会把注意力消耗在理解现有代码上，产出质量明显下降。

## 5. 每项工作的交付要求

### 5.1 必须落盘可验证的产物

每项工作都必须产出**具体路径的文件**，而非"完成某功能"的描述。验收方式是**读该文件**，不是"跑通了"。

### 5.2 验收必须机械可判定

可接受：文件存在于指定路径、内容包含指定段落、命令退出码为 0、字段与 schema 一致。

不可接受："功能正常"、"应该没问题"、"看起来对"。

### 5.3 只报告实际观察到的结果

执行者不得推测。无法验证的部分须明确说明"未验证"及原因。

### 5.4 验证后须清理临时产物

本地服务需关闭；临时数据库、缓存、测试输出需删除。

### 5.5 文件所有权

每项工作有明确的文件范围。**不得修改范围外的文件，尤其不得修改契约层。** 发现契约问题时停止并上报。
